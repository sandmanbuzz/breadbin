## H1: one remaining fail-open input case

But the standalone `--verdict` interface still accepts an empty shard list with `--expect 0`:

- `mapfile -t names < "$out/names"` yields an empty array for an empty file.
- The per-shard loop does nothing.
- An empty `expected_counts` file produces zero seen entries, matching zero names.
- Aggregate total 0 equals expected 0.
- No failure flag is set, so the verdict prints `PASS` and exits 0.

**Reproduction:** I copied the current `verdict()` logic into an isolated Bash harness, supplied empty `names` and `expected_counts` files plus `--expect 0`, and observed:

```

```

This is a malformed-evidence false green in the manual verdict interface, not evidence that an ordinary full shard run can currently produce an empty manifest.

## Dforge: correct the risk classification

I re-read `experiments/iec-stall/dfcopy.py`, its README, and the existing `nibcopy.py` / `write-physical.sh` path.

The local reply says the device-ID collision is confirmed, then classifies it as low-risk. I disagree with that classification:

- `dfcopy.py` explicitly enables Drive A and sets its bus ID to 8.
- The same README documents the physical 1541 as device 8.
- `dfcopy.py` does not renumber or disable the physical drive before the write.
- The documented normal dforge write setup says to disable Drive A and Software IEC, which is the opposite of what this script does.

That is a **blocking topology/safety conflict**, not a low-risk known condition. The script must not be used on the documented normal topology until the actual dforge source/target arrangement is established.

The existing nibbler path is a useful contrast, not a drop-in dforge recipe: `nibcopy.py` moves the physical drive from 8 to 9, gives Drive A bus 8, copies 8→9, then turns Drive A off and resets the physical drive back to 8. `write-physical.sh` acquires the `ultimate` lock and has an EXIT restoration path. Dforge may have different requirements, but it needs an equally explicit, verified device plan.

Other independently visible problems remain:

- No `tools/with-lock -r ultimate` around the job.
- No restoration of KERNAL/Drive A configuration on failure or exit.
- KERNAL setting is changed, but the script calls `u.reset()`; the README says this setting requires `machine:reboot`.
- Pause/DMA/resume sequences lack `try/finally`.
- The write loop catches and discards screen-read exceptions, polls many memory regions every five seconds despite the README's explicit warning not to do long DMA screen reads during disk transfer, and proceeds to RUN/STOP/reset after the 120-second loop even if it never observed completion.
- The final BASIC directory listing only confirms a directory entry; the automation does not read back or compare sectors, and it prints `Done.` without a reliable success/failure decision.

### Request

Please revise the static dforge assessment against the current local tree and the actual documented dforge procedure. In particular:

1. Establish the intended source and target devices and how dforge selects them. Resolve the bus-8 collision rather than calling it low-risk.
2. Compare the required config/lock/pause lifecycle with the proven `write-physical.sh` pattern, noting where dforge needs a different design.
3. Propose a minimal safe execution and verification plan, including timeout/error behavior and the destructive-write authorization boundary.

Investigation only: **do not run `dfcopy.py`, do not access the Ultimate or physical 1541, and do not change hardware configuration or production code.** Report what is verified from source/docs versus what remains unknown until an explicitly authorized hardware test.
