# Breadbin drive-ROM S-ifier

Status: first build-tool slice; **not yet a runnable Breadbin drive ROM**.

This work targets the 1541C/1541-II 32 KiB ROM layout demonstrated by the supplied S-JiffyDOS 1541C image:

| CPU address | Image offset | Purpose |
|---|---:|---|
| $8000-$9FFF | $0000-$1FFF | SJD extension bank `S80-9` |
| $A000-$BFFF | $2000-$3FFF | SJD extension bank `SA0-B` |
| $C000-$DFFF | $4000-$5FFF | Common captured/modified DOS bank `C/C0-DF` |
| $E000-$FFFF | $6000-$7FFF | Derived CBM/JD/SJD DOS bank, selected by ROM configuration |

The supplied JiffyDOS 6.01 dump is 16 KiB and has SHA-256 `2de4d06b4aa2a1b1129cc641a01cbac7e631de362dbd6fe2129eec7336afad53`. The supplied S-JiffyDOS image is a close derivative: 15,261 of 16,384 bytes in its upper bank match. This supports the layout and base-family choice, but does not prove that the SJD generator consumes this exact dump byte-for-byte.

## What exists now

`tools/sjd41/rom_image.py` is a conservative image composer:

- `inspect` reports size, SHA-256 and the NMI/RESET/IRQ vectors.
- `build` accepts a user-supplied 16 KiB JD ROM, our 16 KiB extension bank, and a JSON patch manifest.
- It requires the base SHA-256 to match the manifest exactly.
- Every patch is guarded by expected original bytes; overlapping patches, out-of-bank addresses, length mismatches and stale input bytes are rejected.
- It emits the 32 KiB image as a 16 KiB extension followed by the patched C000-FFFF bank. This is a generic composer, not yet a reproduction of the SJD41 generator's capture and patch stages.
- No CMD/JiffyDOS/S-JiffyDOS ROM bytes or generated derivative are checked in.

The example manifest is deliberately empty. It is a safe image-layout smoke test, **not** a functional S-ifier: a real extension and proven hook patches must be supplied before the result can boot.

`tools/sjd41/generator_records.py` is now a separate reverse-engineering tool. It reads the operator-supplied SJD41 D64, extracts the three appended patch tables, applies Stage 1 and Stage 3 to the supplied JD E000-FFFF bank, and optionally writes/compares the reconstructed 8 KiB output. It embeds and prints no ROM payload bytes.

Example:

```sh
python3 tools/sjd41/rom_image.py inspect JiffyDOS_6.01-1541-and-1541-II.bin

python3 tools/sjd41/rom_image.py build \
  --base JiffyDOS_6.01-1541-and-1541-II.bin \
  --extension breadbin-extension.bin \
  --manifest tools/sjd41/manifest.jd601.example.json \
  --output breadbin-jd601-1541c-private.bin
```

Keep all input ROMs, extension+ROM output images and intermediate combined images local. The upstream S-JiffyDOS instructions explicitly warn that generated images contain CMD JiffyDOS routines and must not be redistributed.

## Important distinction: SJD64 vs SJD41

Jochen Adler publishes two independent patches: SJD64 for the C64 KERNAL and SJD41 for the 1541 drive DOS. The author explicitly says they are independent and that a JD-C64 can be used with an SJD41 drive.

The user-supplied `ajnsjd64.d64` is the **SJD64/C64 generator disk**, not the SJD41 drive generator disk. Its `C2-GEN/JD` and `C3-GEN/SJD/US` programs check for the C64 KERNAL signature `JIFFYDOS V6.01` at `$E4DC` and create C64-side intermediate files. Their code is not evidence for the SJD41 drive-ROM transformation. The earlier C2/C3 disassembly notes below are retained as analysis of that separate C64 toolchain only.

The SJD41 instructions are at https://retro-bobbel.de/nlq/ajnsjd41.html. They state that SJD41:

- patches JiffyDOS 1541 and retains the original JD IEC bus routines;
- works with ordinary JiffyDOS computers and speeder cartridges; SJD64 is not required;
- adds drive-side fast open/load/save, scratch and validate operations, plus GCR-to-HD decoding while reading;
- uses `$8000-$FFFF` on 1541C/1541-II, and `$8000-$FFFF` or `$A000-$FFFF` on the old 1541 depending on whether one or both ROMs are replaced;
- is generated by a separate SJD41 workflow with separate interim files and a separate `EP-GEN/41...` stage.

Therefore, the right source for reconstructing the drive-side transformation is the actual SJD41 generator disk plus the supplied JD and SJD41 drive ROMs. Do not continue reverse-engineering C2/C3 as if they produced the drive ROM.

## What the SJD64 disk analysis found (separate product)

The SJD64 C3 BASIC program checks the exact KERNAL signature `JIFFYDOS V6.01` at C64 address `$E4DC`, loads a 138-byte machine-code routine at `$C000`, executes it, initializes device 8, then saves the memory range `$4000-$5FFF` under a generated filename. The routine copies `$E000-$FFFF` into `$4000-$5FFF`, then performs a further pointer-driven transformation that remains to be fully annotated. C2 uses the same BASIC scaffold but a shorter 29-byte routine. This is useful only if we separately work on the C64-side SJD64 product.

## SJD41 documented behavior and performance baseline

The supplied drive-side instructions file `S41-PCUS.TXT` gives the following timings (seconds; transcribed from that document):

| Operation | CBM 1541 | JD 1541 | SJD 1541 |
|---|---:|---:|---:|
| New/format, 35 tracks | 95.4 | 22.2 | 22.5 |
| Load 202 blocks, at configured gap | 127.2 | 13.2 | 8.7 |
| Load 202 blocks, gap 9.5 | 127.2 | 20.7 | 14.7 |
| Save 154 blocks | 105.3 | 43.4 | 21.0 |
| Scratch 202 blocks | 24.9 | 14.9 | 4.3 |
| Scratch 664 blocks / 144 files | 361.7 | 260.3 | 17.9 |
| Validate 664 blocks / 144 files | 239.0 | 139.6 | 10.9 |
| Find 144th directory file | 5.3 | 4.7 | 1.1 |
| IECOUT, 100 bytes | 0.146 | 0.0335 | 0.0335 |
| IECIN, 100 bytes | 0.204 | 0.0216 | 0.0216 |

The same instructions identify the mechanisms and compatibility caveats:

- Fast open uses gap 3 instead of 22.
- One special LOAD handles PRGs saved with the CBM gap 9.5; another decodes GCR to host-data format while reading and uses gap 4.
- Fast save verifies written blocks. It still uses the original C64-side routines; a long C64 IRQ caused by pressing a key during SAVE can slow the operation.
- Fast scratch and validate calculate checksums while reading disk bytes.
- SJD supports 40 tracks, automatic or fixed track selection, optional use of otherwise-reserved free sectors on directory track 18, GEOS-aware lock/unlock/scratch/validate behavior, three-digit error numbers, and a fast reset without RAM/ROM tests.
- On 1541C/1541-II, SJD uses the full `$8000-$FFFF` ROM area. On the old two-ROM 1541, replacing only one EPROM omits check, fast lock/unlock, fast scratch, fast validate, fast save, and some DOS bug fixes.

For Breadbin, the high-value distinction is that SJD's IEC byte transport is not faster than JD's: its own timing table gives identical 100-byte IECOUT/IECIN times for JD and SJD. The large gains are in DOS/drive-side operations—directory search, scratch/validate, and disk read/write work. That is consistent with preserving Breadbin's existing JiffyDOS byte transport while investigating the drive-side block path.

## SJD41 generator findings

The correct drive-side generator disk, `ajnsjd41.d64`, is now parsed and its staged process is mapped:

1. Stage 1 reads the live drive address window `$8000-$FFFF` in 256-byte pages via a drive-RAM helper and two 128-byte `M-R` transfers per page. It then applies 33 embedded patch records to the captured E000-FFFF bank and manually patches the captured C000-DFFF bank.
2. Stage 2 applies 67 embedded records to the Stage-1 E000-FFFF intermediate to produce the CBM E000-FFFF bank.
3. Stage 3 applies 82 embedded records to the same Stage-1 intermediate to produce the SJD E000-FFFF bank.
4. The final EP-GEN assembles four 8 KiB inputs in address order: S80-9, SA0-B, C/C0-DF, SE0-F.

The shared 138-byte helper interprets records as destination-low, destination-high, length, payload; a zero length byte means 256 bytes. Each BASIC generator contains its record table as a binary trailer immediately after the BASIC end marker.

Applying Stage 1 and Stage 3 to the supplied JD image reconstructs the SJD E000-FFFF bank with only nine differing bytes from the supplied SJD binary: `$EAD5`, `$EBC3-$EBC4`, and `$FA32-$FA37`. The six-byte `$FA32-$FA37` range is the SJD hook: `JMP $C010` plus three NOPs. The routine at `$C010` in the SJD C-bank is a relocation of the 1541C track-zero sensor routine documented at `$FF36`; the 1541-II base ROM lacks that routine. This is now a concrete model-specific transformation, not a failed record interpreter. The two `$EBC3-$EBC4` bytes redirect an existing call from `$F259` to a new wrapper at `$C049`; that wrapper calls `$F259`, then sets zero-page `$06=1` and `$00=$C0`. The remaining `$EAD5` mismatch is in a Stage-3 patch record (reconstruction `$C0`, supplied SJD image `$D0`) and may reflect a generator/image revision difference. One Stage-3 record writes 102 bytes starting at `$7FFF`, spilling 101 bytes beyond the 8 KiB saved bank; the spill's purpose is unresolved.

The C000-DFFF bank differs by 68 bytes after applying the literal first-stage POKEs to the supplied JD image: 67 bytes in `$C010-$C054` and one at `$C0AD`. The `$C010-$C048` bytes are the relocated 1541C track-zero sensor routine; the E-bank hook at `$FA32` jumps to `$C010`. The `$C049-$C054` helper is called from `$EBC2` and wraps `$F259` while setting zero-page state; its caller's broader purpose and the lone `$C0AD` discrepancy still need analysis. The generator captures live drive memory; a matching 1541C/JD capture is the authoritative input. The inspector accepts either a raw capture with `--c000-capture` (applying the POKEs decoded from the D64) or the Stage-1 `(C)CMD/C/C0-DF` PRG with `--c000-intermediate` (already patched).

See `docs/research/sjd41-generator-disk.md` for the full evidence and the local inspector invocation. The original 1541C track-zero sensor routine is documented in [Wolfgang Moser's 1541C-to-1541-II ROM comparison](https://www.zimmers.net/anonftp/pub/cbm/firmware/drives/new/1541/1541C-to-1541-II.txt).

## U1/U2 compatibility consequence

The clean-room DOS source trace shows that Breadbin's ordinary U1 block reads enter the controller READ job (`block.s` → `drtrd` → `doit2`). SJD replaces the READ job's call at `$F4D1` from `$F50A` (`DSTRT`) to `$B2F7`. That extension path tests bit 7 of `$1C0A` (VIA2 shift register): one branch falls back to the stock sync/read path, while the other reads the GCR block via `$B2C0`, decodes it via `$B132` using tables at `$BA00` and `$BC00`, and returns to the common read completion path. Therefore U1 reads enter the SJD read dispatcher and are eligible for the optimization when its condition is satisfied, without any Breadbin host protocol change.

The U2 write path enters `WRIGHT` at `$F56E`. Its main GCR emission loop and `JSR $F510` search call remain byte-identical to JD, but WRIGHT then calls `WTOBIN` to restore the data buffer and schedules a verify job. SJD changes the `WTOBIN` tail at `$F674-$F682` to route through the ATN-service routine at `$E85B`; the verify job at `$F691` still calls stock `$F50A` directly and compares encoded bytes rather than using `$B2F7`. SJD also clears a BINGCR tail that appears unused on the ordinary path. So U2 has a small buffer/ATN-path change, but no clear fast-write acceleration is established. Measure U1 and U2 separately on VICE and the C64 Ultimate.

## Read-hook smoke image

A behavior-preserving 32 KiB test image can validate the ROM bank layout and hook ABI before any real read optimization is written:

`python3 tools/sjd41/read_hook_smoke.py \
  --base JiffyDOS_6.01-1541-and-1541-II.bin \
  --output /tmp/breadbin-read-hook-smoke.bin \
  --extension-output /tmp/breadbin-read-hook-extension.bin \
  --manifest-output /tmp/breadbin-read-hook-smoke.json`

The only patch is `$F4D1`: stock `JSR $F50A` becomes `JSR $B000`. The extension trampoline at `$B000` is `JMP $F50A`, so the original JiffyDOS routine executes unchanged and returns to the original caller. The rest of the 16 KiB extension bank is `$FF`. This is strictly an emulator smoke test: it adds no feature or speedup and must not be burned as a production ROM.

## U1/U2 validation plan

The supplied SJD instructions expose an `sj` on/off setting and a separate `ic` JD/CBM IEC-bus setting. Keep the IEC setting fixed to JD while testing the drive-side read optimization. Do not assume the `sj` command spelling from the PETSCII-rendered text until its exact bytes are decoded.

1. Use the same disk image and device configuration for JD and SJD.
2. Run Breadbin U1 against a fixed known-good track/sector, verify the 256-byte checksum, and time repeated reads. Repeat with SJD mode enabled and disabled if possible.
3. Run U2 only against a disposable image or scratch sector. Verify the write by reading it back, compare checksums, and restore the original image afterward.
4. Record read/write elapsed time separately. Do not infer U2 performance from file SAVE timings.
5. Run first in VICE, then on the C64 Ultimate if results agree.

Expected from static analysis: U1 enters the SJD read dispatcher and may take its GCR-to-HD path; U2 uses stock write emission and verify with a small ATN/buffer-restoration modification. The benchmark is still required to establish actual gains and verify fallback behavior.

## First SJD41 hook map

The supplied SJD image confirms the intended design pattern: preserve the JD DOS/IEC foundation, redirect selected DOS paths into extension-bank code, and return through ordinary DOS machinery where appropriate. The first statically confirmed extension call-ins are:

| Existing DOS hook | Extension entry | Status |
|---|---:|---|
| `$FB15` | `$A003` | Format-track path trampoline from the original `FORMT` routine; extension behavior still to disassemble |
| `$F15C` | `$B4DD` | Replaces the disk-full path; scans tracks 36-40 before failing, confirming 40-track overflow handling |
| `$F173` | `$B842` | Replaces `FNDNXT`, the optimum next-sector allocator; uses sector increment and track geometry, consistent with configurable gap/interleave |
| `$F4D1` | `$B2F7` | Replaces `DSTRT` in the standard controller READ job with the SJD GCR-to-HD read path |
| `$FA32` | `$C010` | Confirmed 1541C track-zero routine relocation |
| `$EBC2` | `$C049` | Confirmed wrapper around `$F259` that sets zero-page state |
| `$DCD6` | `$C075` | Short DOS job/status cleanup helper |

The `$E91D-$E998` replacement is a serial-bus/handshake path candidate, not the GCR decoder: it uses VIA/IEC-related registers and calls the `$E9xx` and `$FEF3/$FEFB` helpers. The actual GCR-to-HD decoder is in the extension bank, reached through the standard read-job hook `$F4D1 -> $B2F7`; `$B2F7` reads GCR through `$B2C0`, decodes through `$B132`, then rejoins the common read completion path. The nearby `$E781-$E7A1` patch also reconfigures VIA registers and appears related to serial/controller signaling.

Other confirmed replacements align with SJD's documented feature set: `$E6D1` redirects `BCDDEC` to the three-digit error formatter; `$EBFC` redirects `PARSXQ` to the extension command parser; `$EE3D` redirects `FORMAT`; `$EF28` redirects `AVCK`; `$EF3A` redirects `SETBPT`; `$EF4F` redirects `NUMFRE`; and `$EFC5` redirects the disk-full check. These are the expected hooks for error reporting, SJD commands, format, and extended BAM/track geometry. The complete candidate inventory is in the research note; the raw scanner deliberately marks unverified byte patterns as candidates.

The first three are the key extension-bank entries for further analysis, but they are not all read paths. `$A003` is reached from FORMAT; `$B4DD` is the 40-track disk-full fallback; `$B842` is the next-sector allocator. The GCR-to-HD read path is `$F4D1 -> $B2F7 -> $B2C0/$B132`; `$E91D-$E998` is a separate serial-bus/ATN path. This corrects the earlier tentative classification of `$FB15` as a fast-load hook and `$E91D` as the GCR decoder. Do not bake guessed behavior into Breadbin's implementation. See the hook table and evidence in `docs/research/sjd41-generator-disk.md`.

## Next implementation gates

1. Resolve the nine E000-FFFF byte differences and the C000-DFFF source discrepancy; obtain a full, model-correct captured input if needed.
2. Disassemble the changed SJD41 drive-ROM regions against the exact captured JD/CBM baseline, mapping new routines, hooks, and call paths.
3. Separate SJD's transparent DOS optimizations from optional features Breadbin does not need.
4. Benchmark U1 and U2 separately. U1 statically enters the SJD read dispatcher and conditional GCR decode path; U2 retains stock write emission/verify with a small ATN/buffer-restoration change.
5. Only if U1/U2 need an additional operation, define a Breadbin-specific ABI and byte-verified hooks. Keep the existing JiffyDOS host byte protocol unchanged.
6. Build private images and test them in VICE, then the C64 Ultimate emulated drive, before physical hardware.

The intended transport boundary remains unchanged: preserve JiffyDOS's existing IEC bus routines and Breadbin's host-side byte transport. SJD41 itself is designed to retain that transport. A Breadbin-specific drive command is a separate design choice, not something to assume from SJD41.
